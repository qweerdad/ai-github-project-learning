AI 协作记录：README 说能直接打开，实际却打不开#

注意：教学示范

性质声明：这是教学模拟记录，不是某次真实 AI 调用的截图或转录。其中"学生"的观察步骤、file:// 报错、源码位置和最终结论均来自本教程制作时对固定版本 40dcd30 的真实实验（第三章有对应截图：file:// 直开与 DevTools CORS 报错）；"AI 的回答"是按主流 AI 的典型表现构造的教学文本。步骤、证据、结论真实，对话本身为示范。

1. 最初遇到的具体问题#

学生按 README 操作：克隆仓库后双击 index.html——页面看起来完全正常，没有任何报错弹窗，但所有交互都失效：输入任务按 Enter 没反应，计数器不工作。

2. 学生自己先做的观察与判断#

发问之前先做的事（顺序很重要）：

  1. 反复确认操作没错：确实是双击打开的、页面确实渲染了；

  2. 看地址栏：URL 是 file:///...index.html——注意到不是 http 开头；

  3. 按 F12 打开 DevTools → Console 有一条红色报错：

    text
    Access to script at 'file:///.../script.js' from origin 'null'
has been blocked by CORS policy: Cross origin requests are only
supported for protocol schemes: chrome, chrome-extension,
chrome-untrusted, data, http, https, isolated-app.

  4. 假设：页面能显示说明 HTML/CSS 加载了，失效的是 JS；报错说 script.js 被 CORS 拦了——而 README 说"直接打开即可"，两者矛盾。可能是：(a) 我环境特殊；(b) README 过时了；(c) 这个项目本来就需要服务器。

3. 实际发给 AI 的问题#

想一想

我在学习一个开源的纯前端任务管理器（HTML/CSS/JS，无框架无构建步骤）。README 写着 "Clone the repository and open index.html in any modern browser"。我照做后页面能渲染，但所有交互失效。

证据：Edge 地址栏是 file:///D:/.../index.html；F12 Console 报错 Access to script at 'file:///.../script.js' from origin 'null' has been blocked by CORS policy。

问题：为什么会这样？最小的解决办法是什么？我不想装一堆东西。

注意这条问题的构成：目标（跑起来）+ 上下文（什么项目、README 怎么写的）+ 证据（file:// 地址、报错原文）+ 约束（最小方案）——就是第五章那个公式。

4. AI 的典型回答与关键建议#

说明

index.html 里多半用了 <script type="module" src="script.js">。ES 模块受 CORS 策略约束，file:// 协议的 origin 是 null，浏览器会拒绝加载模块脚本。HTML 和 CSS 不受影响，所以页面"看起来正常"。

最小方案：在项目目录起一个静态服务器，让页面从 http://127.0.0.1 访问。Python 装了的话一条命令即可：python -m http.server 8765 --bind 127.0.0.1，然后访问 http://127.0.0.1:8765/。

5. 哪些经过了源码与运行验证（不能只听 AI）#

AI 的说法 验证方法 结果
"用了 type="module"" 打开 index.html 搜 script ✅ 确有 <script type="module" src="script.js">
"file:// 下模块会被 CORS 拦" 与 Console 红字逐词比对 ✅ 报错对象正是 script.js
"起本地服务器能解决" python -m http.server --bind 127.0.0.1 → 访问 http://127.0.0.1:8765 ✅ 交互全部恢复，Console 无报错
（推论）README 写得不准确 对照固定 commit 的 README 原文 ✅ README 确实只写了 "open index.html"，没提模块限制

6. AI 回答里需要警惕/修正的地方#

构造的这段回答基本是准的，但实战中同类问题 AI 常犯的错：

  • 把小概率原因排前面：有些 AI 会先说"可能浏览器太旧/缓存问题，清一下缓存"——如果先信了这句去清缓存，问题照旧。识别方法：它已经给了你具体机制（module + CORS），就该先验证机制而不是照单全收所有建议。
  • 过度方案：有的 AI 会让你 npm init + npm install live-server + 写配置文件——对一个零依赖项目是杀鸡用牛刀。约束条件"最小方案"要在提问里写死。
  • README 一定对的默认假设：AI 倾向于解释"README 为什么这样写"，而不是指出"README 和源码矛盾"。这个矛盾要学生自己发现——这就是第三章把这个案例单列出来的原因。

7. 可迁移的方法总结#

text
官方文档与实测不符时的排查链：
文档写了什么 → 照做 → 异常现象原样记录 → 提假设 →
带证据问 AI → 回源码搜证（Ctrl+F）→ 最小方案 → 再实测

三点迁移价值：

  1. README 不是真理，源码和运行才是——文档会过时，机器报错不会撒谎；
  2. 报错原文是最值钱的提问素材——origin 'null'、CORS、protocol schemes 三个词就把问题锁死了；
  3. "页面正常但功能死"是 JS 没跑起来的典型症状——以后在任何项目里见到都应先查 Console。

8. 检查清单（自己复做一遍）#

  • 双击 index.html，观察"假正常"现象；
  • F12 找到 CORS 红字并抄录原文；
  • 在 index.html 里搜到 type="module" 这一行；
  • 用 --bind 127.0.0.1 起服务器后确认交互恢复；
  • 能用一句话向同学解释：为什么 HTML 能显示而 JS 不能跑。
